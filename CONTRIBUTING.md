## Getting Started

Zorilla is a monorepo managed with [pnpm workspaces](https://pnpm.io/workspaces). All packages live in the `packages/` directory.

### Prerequisites

- Node.js 20 or higher
- pnpm 9 or higher

### Initial Setup

```bash
# Clone the repository
git clone https://github.com/zorillajs/zorilla.git
cd zorilla

# Install dependencies
pnpm install

# Build all packages
pnpm build

# Run tests to verify everything works
pnpm test
```

## Development Workflow

### Building Packages

```bash
# Build all packages
pnpm build

# Build a specific package
cd packages/puppeteer-extra-plugin-stealth
pnpm build
```

### Running Tests

```bash
# Run all tests across all packages
pnpm test

# Run tests with coverage
pnpm -r run test:coverage

# Run tests in a specific package
cd packages/puppeteer-extra
pnpm test

# Run tests in watch mode (for development)
cd packages/puppeteer-extra
pnpm test:watch
```

### Linting and Formatting

We use [Biome](https://biomejs.dev/) for linting and formatting:

```bash
# Check for issues (no changes)
pnpm check

# Auto-fix issues
pnpm fix

# Check links in markdown files
pnpm links
```

## Creating Changesets

We use [Changesets](https://github.com/changesets/changesets) for version management. When you make changes that should trigger a release, you need to create a changeset.

### When to Create a Changeset

Create a changeset if your changes include:
- **Bug fixes** (patch version bump)
- **New features** (minor version bump)
- **Breaking changes** (major version bump)

You do **not** need a changeset for:
- Documentation updates
- Test changes (without code changes)
- Build configuration changes
- Development tooling updates

### How to Create a Changeset

```bash
# Run the changeset CLI
pnpm changeset

# You'll be prompted to:
# 1. Select which packages changed
# 2. Choose bump type (major/minor/patch)
# 3. Write a summary of the changes
```

**Example:**

```bash
$ pnpm changeset

🦋  Which packages would you like to include?
◯ changed packages
  ◉ @zorilla/puppeteer-extra-plugin-stealth
  ◯ @zorilla/puppeteer-extra-plugin-recaptcha

🦋  What kind of change is this for @zorilla/puppeteer-extra-plugin-stealth?
  ◯ major (breaking change)
  ◉ minor (new feature)
  ◯ patch (bug fix)

🦋  Please enter a summary for this change:
Add new navigator.webdriver evasion technique

🦋  Changeset created! ✨
```

This creates a file in `.changeset/` that will be used during the release process.

### Commit the Changeset

```bash
git add .changeset/*.md
git commit -m "chore: add changeset"
git push
```

## Publishing Process

Publishing is **fully automated** via GitHub Actions using **npm trusted publishing with OIDC** (no tokens required).

### How It Works

1. **Developer creates changes** with conventional commits and changesets
2. **PR is merged to `main`** branch
3. **GitHub Action runs** and creates a "Version Packages" PR
   - Updates package versions
   - Generates changelogs
   - Updates dependencies
4. **Maintainer reviews and merges** the "Version Packages" PR
5. **GitHub Action automatically publishes** to npm with automatic provenance attestations

### npm Trusted Publishing Setup (One-Time Configuration)

For each package in the monorepo, maintainers must configure trusted publishing on npmjs.com:

1. Navigate to the package settings on npmjs.com
2. Locate the **Trusted Publisher** section
3. Add a new trusted publisher with:
   - **Organization or user**: `zorillajs`
   - **Repository**: `zorilla`
   - **Workflow filename**: `release.yml`
   - **Environment name**: (leave blank)

This configuration allows the GitHub Actions workflow to publish without storing any npm tokens. Authentication happens via OIDC tokens generated by GitHub Actions.

**Requirements:**
- npm CLI version 11.5.1 or later (automatically handled in CI)
- `id-token: write` permission in workflow (already configured)

### Manual Publishing (First Publish or Emergency)

For the initial publish of a package or emergency situations:

```bash
# Make sure you're signed into npm
npm whoami

# Ensure everything is built and tested
pnpm install
pnpm build
pnpm test

# Publish manually
pnpm changeset publish
```

**Note:** After the first manual publish, configure trusted publishing on npmjs.com for that package to enable automated CI/CD publishing.

## Creating a Plugin

The plugin API for puppeteer-extra is clean and powerful. Here's how to create a new plugin:

### 1. Set Up Your Plugin Package

```bash
# Create a new directory
mkdir packages/puppeteer-extra-plugin-myplugin
cd packages/puppeteer-extra-plugin-myplugin

# Initialize package.json
pnpm init
```

### 2. Plugin Structure

```typescript
import { PuppeteerExtraPlugin } from '@zorilla/puppeteer-extra-plugin'

class Plugin extends PuppeteerExtraPlugin {
  // Required: plugin name (convention: matches package name without prefix)
  get name() {
    return 'myplugin'
  }

  // Optional: default options
  get defaults() {
    return {
      enabled: true,
      customOption: 'default value'
    }
  }

  // Optional: plugin requirements
  get requirements() {
    return new Set(['runLast', 'dataFromPlugins'])
  }

  // Optional: plugin dependencies
  get dependencies() {
    return new Set(['user-data-dir'])
  }

  // Lifecycle hooks (all optional)
  async beforeLaunch(options) {
    // Modify launch options before browser starts
    this.debug('beforeLaunch called', options)
  }

  async afterLaunch(browser, options) {
    // Do something after browser launches
    this.debug('browser launched', browser)
  }

  async onPageCreated(page) {
    // Called for each new page
    this.debug('page created', page.url())

    // Use this.opts to access merged options
    if (this.opts.enabled) {
      await page.evaluateOnNewDocument(() => {
        // Your page modification code
      })
    }
  }

  // Expose data for other plugins
  get data() {
    return [
      {
        name: 'myData',
        value: { /* data object */ }
      }
    ]
  }
}

// Export factory function
export default (opts) => new Plugin(opts)
```

### 3. Plugin Lifecycle Events

Available lifecycle hooks:
- `beforeLaunch(options)` - Modify launch options (waterfall)
- `afterLaunch(browser, options)` - Post-launch actions
- `beforeConnect(options)` - Modify connect options (waterfall)
- `afterConnect(browser, options)` - Post-connect actions
- `onBrowser(browser, options)` - Called for any browser acquisition
- `beforeContext(options)` - Before context creation (Playwright)
- `onContextCreated(context)` - Context created (Playwright)
- `onPageCreated(page)` - New page created
- `onTargetCreated(target)` - New target created
- `onPageClose(page)` - Page closed
- `onDisconnected()` - Browser disconnected

### 4. Using Debug Logging

```typescript
// In your plugin
this.debug('message', { data: 'value' })

// Users enable with:
// DEBUG=puppeteer-extra-plugin:myplugin node script.js
```

### 5. Testing Your Plugin

```typescript
import { test, expect } from 'vitest'
import puppeteer from '@zorilla/puppeteer-extra'
import MyPlugin from '../src/index.js'

test('plugin works', async () => {
  puppeteer.use(MyPlugin())
  const browser = await puppeteer.launch({ headless: true })
  const page = await browser.newPage()
  // ... test your plugin functionality
  await browser.close()
})
```

### 6. Plugin Examples

Check out these plugins for reference:
- **Simple:** [`puppeteer-extra-plugin-anonymize-ua`](./packages/puppeteer-extra-plugin-anonymize-ua) - Modify user agent
- **Moderate:** [`puppeteer-extra-plugin-block-resources`](./packages/puppeteer-extra-plugin-block-resources) - Request interception
- **Complex:** [`puppeteer-extra-plugin-stealth`](./packages/puppeteer-extra-plugin-stealth) - Multiple evasions with sub-plugins

## Code Standards

### Linting

We use **Biome** for linting and formatting:

```bash
pnpm check       # Check for issues
pnpm fix         # Auto-fix issues
```

Configuration is in `biome.json` at the repo root.

### TypeScript

- All packages use TypeScript with strict mode
- Type definitions are generated automatically
- Use proper types, avoid `any` (use `biome-ignore` comment if absolutely necessary)

### Testing

- **Coverage requirement:** Most packages require 90-100% coverage
- **Test framework:** Vitest (most packages) or @playwright/test (playwright-extra)
- Tests must pass on Node 20 and 22, across Linux, macOS, and Windows

### File Structure

```
packages/my-plugin/
├── src/
│   ├── index.ts          # Main plugin file
│   └── lib/              # Optional helper modules
├── test/
│   └── index.test.ts     # Tests
├── package.json
├── tsconfig.json
├── vitest.config.ts      # Test configuration
└── README.md             # Plugin documentation
```

## Commit Messages

We recommend using [Conventional Commits](https://www.conventionalcommits.org/) for clarity:

### Format

```
<type>(<scope>): <subject>

<body>

<footer>
```

### Types

- `feat`: New feature
- `fix`: Bug fix
- `docs`: Documentation changes
- `test`: Test changes
- `chore`: Build, CI, or tooling changes
- `refactor`: Code refactoring
- `perf`: Performance improvements
- `style`: Code style changes (formatting, etc.)

### Examples

```bash
# Feature
git commit -m "feat(stealth): add navigator.webdriver evasion"

# Bug fix
git commit -m "fix(recaptcha): handle timeout errors gracefully"

# Breaking change
git commit -m "feat(puppeteer-extra)!: remove deprecated launch option

BREAKING CHANGE: The deprecated 'headless' string option is removed. Use boolean instead."

# Scoped to package
git commit -m "docs(plugin-base): update lifecycle hook documentation"

# Multiple files
git commit -m "chore: upgrade dependencies across all packages"
```

## Pull Request Process

1. **Fork the repository** and create a branch from `main`
2. **Make your changes** following the code standards above
3. **Add tests** for any new functionality
4. **Create a changeset** if your changes warrant a version bump
5. **Ensure all tests pass**: `pnpm test`
6. **Ensure linting passes**: `pnpm check`
7. **Create a pull request** with a clear title and description

### PR Title Format

Use conventional commit format for PR titles:

```
feat(stealth): add new evasion technique
fix(recaptcha): resolve timeout issue
docs: update contributing guide
```

### What Happens Next

1. Automated tests run on your PR (Linux, macOS, Windows × Node 20, 22)
2. Maintainers review your code
3. Once approved and merged, the release process kicks in automatically
4. Your contribution will be included in the next release with proper changelog entry
